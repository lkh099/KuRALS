# NPU simulation handoff — R64-D8 / D16 / D32

What to copy to the NPU sim server, what each file means, and how to regenerate it.
Everything here is resolution-agnostic: nothing assumes an 8x64 grid.

## Packages

| package | grid | width | MACs | peak NPU buffer | int8 replay test mIoU | source run |
|---|---|---|---|---|---|---|
| `model_release_v01` | R64-D8 | 0.5x | 1,569,280 | 16,384 B | 0.6002 | `Q_…wm0.5_ss1_R64-D8_qlr0.0001_s44` |
| `model_release_w1.0_v01` | R64-D8 | 1.0x | 4,952,576 | 32,768 B | 0.6152 | `Q_…wm1.0_ss1_R64-D8_qlr1e-05_s45` |
| `model_release_d16_v01` | R64-D16 | 0.5x | 3,138,560 | 32,768 B | 0.5939 | `Q_…wm0.5_ss1_R64-D16_qlr0.0001_s45` |
| `model_release_d32_v01` | R64-D32 | 0.5x (stem_stride 2) | 1,569,280 | 16,384 B | 0.3262 | `Q_…wm0.5_ss2_R64-D32_qlr0.0001_s44` |
| **`model_release_d32_w0.25_v01`** | R64-D32 | **0.25x (stem_stride 1)** | 2,246,656 | 32,768 B | **0.5003** | `QW_…wm0.25_ss1_R64-D32_qlr0.0001_s45` |

**Use `model_release_d32_w0.25_v01` for D32 work.** `model_release_d32_v01` is kept because it is
the pre-registered design-point package the paper's tables refer to, but its stride-2 head caps its
accuracy (see the caveats) and the 0.25x stride-1 package is +0.174 replay mIoU at the same grid.

All five pass `gen_cfg.py` allocation at 32 KiB with CUTPOINT 3 and 23 layers.

**`gen_cfg.py` is not in this repo.** It is NPU8's own config generator and lives in the separate
`npu_riscv` repository, at `$NPU_RISCV_CFG_DIR` (default `~/xsrc/ext/npu_riscv/cfg_generator`);
`kurals/npu_check.py` shells out to it. Clone `npu_riscv` alongside this repo, or point
`NPU_RISCV_CFG_DIR` at it, before running any legality check. The `kurals/cfg_gen.py` in this repo
is an older vendored copy kept for reference -- it has no command-line interface and differs from
the authoritative generator; prefer `gen_cfg.py`.
**D16 and the 1.0x design sit exactly at the 32,768 B bank limit, with no headroom.**

Each package contains `architecture.json` (per-layer shapes, shifts, scales, fusion flags),
`weights_int.bin` / `scales.bin` / `biases.bin`, `quantization.json`, `preprocessing.json`
(input contract), `class_map.json` (output contract), `sample_inputs/`, `golden_outputs/`,
`golden_layer_outputs/`, `metrics.json` and `config.yaml`. `npu_cfg.c` is generated on demand
from the manifest by `gen_cfg.py`; it is not checked in. Each package also carries its own
`README.md` (generated by `exp03/make_package_readme.py`) with its scales, sizes and limits.

Rebuild any of them:

```bash
python exp03/make_release.py --run <QAT run tag> --out exp03/model_release_<name>
# a grid with no preset config in exp03/configs/:
python exp03/make_release.py --run <tag> --out <dir> \
    --range-bins 128 --doppler-bins 64 --dataset-root /path/to/KuRALS_CW
```

`make_release.py` takes the grid from the run tag (`R<range>-D<doppler>`) and the dataset root
from `exp03/configs/rd_r<W>_d<H>.yaml`; `--range-bins` / `--doppler-bins` / `--dataset-root`
override both. The release is verified by replaying the exported integers over the whole Test
split and comparing against the QAT simulation (`pixel_agreement_with_qat_sim` in
`metrics.json`; 1.000000 for D16/D32/1.0x, 0.999993 for D8).

## Driving a package without a checkpoint

`exp03/load_release.py` reads a package back into the `(arrays, manifest)` pair that
`kurals/int8_inference.py` consumes, so the exact-integer reference can be replayed from the
package files alone. Verified bit-exact against every package's own `golden_outputs`:
**max |diff| = 0.0** on all 8 samples of all four packages, argmax agreement 1.000000.

```bash
python exp03/load_release.py --package exp03/model_release_d32_v01              # all samples
python exp03/load_release.py --package exp03/model_release_d32_v01 --sample 0 --layers
```

`--layers` compares all 23 layers against `golden_layer_outputs/`, which is what you want when a
hardware or simulator mismatch has to be localised to a layer rather than just observed at the
output. Reading a package needs only numpy; replaying it also needs torch, because
`int8_inference.py` runs the convolutions in float64 (exact for this network — see its docstring).

`--emit-export` writes the `<prefix>.npz` + `<prefix>.json` pair that `kurals/export_int8.py`'s
own `main()` produces, for any consumer of that format — an RTL preload reading
`kurals_int8.{json,npz}`, for instance:

```bash
python exp03/load_release.py --package exp03/model_release_d32_w0.25_v01 --emit-export out/kurals_int8
```

The emitted manifest carries the **`input_contract`** block that npu_riscv's `e2e_golden`
consumers require: `sim/e2e_golden/generate_raw_to_track.py` refuses a manifest whose
`input_contract.type` is not `dsp_log2_5p3`, and `generate_conformance.py` cross-checks
`dsp_log_scale` against the scenario. The emitted block is compared field-for-field against the
deployed reference in `sim/e2e_golden/releases/raw_to_track_v2/model/kurals_int8.json` and matches
it exactly, as do the manifest's top-level and per-layer key sets. Every field is derived from the
package — `dsp_log_scale` and `proxy_power_right_shift` are parsed out of `preprocessing.json`'s
contract string, so a package built at a different LOG_SCALE reports its own value, and the two
Doppler orders are asserted rather than assumed, so a package whose preprocessing stops matching
raises instead of emitting a contract that disagrees with its own data.

Output directories are created as needed, so `--emit-export` and `--emit-manifest` can write to a
path that does not exist yet.

The same script regenerates the NPU config from a package, no checkpoint involved:

```bash
python exp03/load_release.py --package exp03/model_release_d32_v01 --emit-manifest /tmp/d32.json
python kurals/manifest_to_cfg_input.py /tmp/d32.json --out /tmp/d32_cfg_input.txt
python $NPU_RISCV_CFG_DIR/gen_cfg.py --input /tmp/d32_cfg_input.txt --output npu_cfg.c \
    --width 64 --height 32 --cutpoint 3 --buf-size 0x8000 --pf 8
```

Checked end to end for D32: that produces a 373-line `npu_cfg.c` and reports Buffer1 = Buffer2 =
16,384 B against the 32,768 B limit, matching the package's own `metrics.json -> npu_check`. Use
`--width <range bins> --height <Doppler bins>`; CUTPOINT is 3 for every package here (see
`CLAUDE.md` for why that value is forced). The committed
`kurals/input/kuralsnet_npu_seg_8x64.txt` predates the eltwise-add legality guard -- it contains
three illegal `activation=leaky` shortcuts and must not be fed to the generator. Regenerate from a
package instead.

Each package also carries its source checkpoint as `checkpoint.pt` (about 120 KB), which is only
needed to build a live torch model — to re-export, to run the float QAT simulation, or to
fine-tune further. It is not needed for the integer replay or for the config chain above.

## Example IFMs

`exp03/example_ifm/<H>x<W>/` — 16 examples per grid (8 synthetic + 8 real), three files each:

| file | what | consumed by |
|---|---|---|
| `<name>_int8.npy` | `(1, H, W)` int8 codes in [0,127] | the model / `kurals/int8_inference.py` |
| `<name>_npu_u32.bin` | `4*H*W` B, Doppler-major, `4*(d*W + r) + ch` | the NPU first-layer DMA (`CTRL[2]=1`) |
| `<name>_raw_u32.bin` | `4*H*W` B, range-major, `4*(r*H + d)`, LE uint32 | DSP bring-up mode (`CTRL[2]=0`) |

Frame size is `4*H*W` bytes in both modes: 2,048 B at 8x64, 4,096 B at 16x64, 8,192 B at 32x64.
The raw and int8 frames of a synthetic example are consistent — the codes are exactly what the
hardware quantizer produces from that raw frame at the given `LOG_SCALE` — so either mode can
be driven and the network sees the same input. Synthetic patterns: `zeros`, `noise_floor`,
`range_ramp`, `doppler_ramp`, `corner_markers`, `targets`, `random`, `saturate`; the ramps and
`corner_markers` are orientation/transpose checks, `saturate` clamps every cell to 127.

```bash
python exp03/make_example_ifm.py --log-scale 0                   # the three study grids
python exp03/make_example_ifm.py --grids 8x64,64x128 --log-scale 0
```

**LOG_SCALE is 0 everywhere.** The committed set was previously generated at `--log-scale 22`
while every package's own contract, and the real frames copied out of those packages, use 0 — so
the synthetic and real inputs in one directory did not share a quantizer setting. The whole set is
regenerated at 0, `manifest.json` records `log_scale: 0`, and it now matches the packages'
`preprocessing.json` and the `input_contract` block above. Check `manifest.json`'s `log_scale`
before reading anything into a synthetic frame's codes.

The real frames come out of a release package's `sample_inputs/`, and an IFM depends only on the
RD grid, not on the model, so one set serves every package at that grid. `manifest.json` records
this per grid under `real_frame_sources`: which package the frames were taken from, the sample
set's SHA-256, and every package verified byte-identical to it. At 32x64 that is both
`model_release_d32_v01` and `model_release_d32_w0.25_v01`, so the `real_model_release_d32_v01_*`
files are the correct real input for the 0.25x model too despite the name; the generator warns
loudly if a package's sample set ever stops matching.

Contract and byte layout: `npu_riscv docs/integration/radar_dsp_npu_input.md`. The generator
implements that document's `log8()` and `q = clamp(log8(P) - LOG_SCALE, 0, 127)` directly, and
the packing is unit-checked against the stated byte addresses.

## Caveats to carry across

* **No NPU cycle or latency number exists for any of these models.** Do not infer one from the
  MAC count; measure it.
* **D32's package is from a stride-2 head, and a better D32 configuration now exists.** Its
  output head runs at /2 and the logits are nearest-upsampled, so every 2x2 output block is
  identical, which caps per-class IoU at 1/4 for a one-pixel target. Its low accuracy is that
  head geometry, not evidence about Doppler information content.

  The earlier claim here — that *every* stride-1 candidate at D32 exceeds the 32,768 B bank
  limit — was wrong, because the pre-registered width grid started at 0.5. **Width 0.25 with
  stem_stride 1 fits at exactly 32,768 B** (2.25 M MACs) and is far better:
  int8 QAT test mIoU **0.4919 +- 0.0730** over seeds 43-45 against this package's
  **0.3212 +- 0.0307**, i.e. +0.1707 +- 0.0428 paired by seed, with all three seeds improving
  and FP32 moving too (+0.0972). See `exp03/summaries/width025_d32.json` and
  `exp03/width025_d32.py`. **That package is now built: `model_release_d32_w0.25_v01`**, from
  `QW_kuralsnet_npu_seg_wm0.25_ss1_R64-D32_qlr0.0001_s45` (seed 45 is the best-*validation* seed of
  the three, val 0.5358; an earlier note here said seed 44, which is the best-*test* seed — the
  project's selection rule is validation, so 45 is correct). Its exact-integer replay over the
  whole D32 Test split gives test mIoU **0.5003** against this package's 0.3262. It sits at the
  bank limit with no headroom (buf1 = buf2 = 32,768 B), like the D16 and 1.0x packages.
* **The D16/D32 QAT re-run is finished and changed nothing** (`exp03/qat_redo_d16_d32.py`,
  results in `exp03/summaries/qat_redo_d16_d32.json`). Seeds 43-45 were re-fine-tuned at QAT LR
  3e-5 and 1e-5 for both grids; neither beat the 1e-4 runs on validation, so both packages above
  keep their original sources. At D32 the QAT LR axis turned out to carry no signal at all: the
  per-epoch validation curves are flat from epoch 20 to 100, and the mean within-run standard
  deviation (0.0112) exceeds the spread of the nine run means (0.0082). Treat a single D32 run's
  best-validation number as a draw from a 0.3026 +- 0.011 band, not as a model ranking.
* **D32's trainer-recorded test mIoU (0.3482) does not match its replay (0.3262).** Replay and
  QAT simulation agree exactly with each other, so the discrepancy is in the trainer's
  evaluation path, not in quantization. The same class of gap exists for the 1.0x package
  (0.5947 recorded vs 0.6152 replayed) and is unexplained; quote the replay number, which is
  the one that was verified end to end.
* All RD inputs are block-max-pool emulations of the native KuRALS-CW map, **not** native SoC
  FFT output. See the SoC caveat in `CLAUDE.md`.
